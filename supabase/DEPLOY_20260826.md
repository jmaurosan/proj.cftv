# Implantação do schema 2026.08.26.4

Este lote deve ser executado no projeto Supabase `tbnuacrwsupkxxhygyko`, nunca
no projeto ClassTower. Use o SQL Editor ou uma CLI autenticada com acesso ao
projeto CFTV.

Antes de começar, confirme que as fases multi-tenant 1 a 3 e as migrations de
canais analógicos/IP e canais BNC desativados já foram aplicadas.

## Ordem obrigatória

Execute cada arquivo separadamente e interrompa na primeira falha:

1. `migration_multi_tenant_04_role_permissions.sql`
2. `migration_credentials_hik_connect_fields.sql`
3. `migration_credentials_secure_access.sql`
4. `migration_atomic_camera_channel_swap.sql`
5. `migration_atomic_camera_connections.sql`
6. `migration_release_baseline_20260824.sql`
7. `migration_custom_site_types.sql`
8. `migration_custom_site_types_length_fix.sql`
9. `migration_network_diagnostics.sql`
10. `migration_network_diagnostics_delete_policy.sql`
11. `migration_equipment_history_commissioning.sql`
12. `migration_commissioning_media_issues.sql`
13. `migration_maintenance_history.sql`

O contrato final só registra a versão `2026.08.26.4` quando todas as tabelas,
colunas e funções obrigatórias já existem. Ele roda em transação e falha sem
registrar a versão quando o schema está incompleto.

## Verificação

Depois da aplicação, execute `verify_release_baseline_20260824.sql`.

O resultado esperado é:

- `schema_version` igual ou superior a `2026.08.26.4`;
- todos os itens de contrato com `is_ready = true`;
- usuário `authenticated` autorizado a consultar a versão e usar as funções
  transacionais;
- usuário `authenticated` sem permissão para inserir versões manualmente.

Somente depois dessa verificação publique o frontend que exige
`REQUIRED_SCHEMA_VERSION = 2026.08.26.4`.

## Retorno seguro

Se uma migration falhar, não publique o frontend novo. Corrija a migration e
continue a partir dela. Para falha específica durante a troca das policies
multi-tenant, use `migration_multi_tenant_03_rollback.sql` e verifique novamente
o acesso antes de prosseguir.
